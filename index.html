  **default-defer** (§10.4). The value is real but narrow. Revisit triggers:

  Impact line: revenue — none direct; delivery — protects integration
  tooling quality if ever adopted; reliability — potential reduction in
  silent script defects; capability — a coding leg we currently cover
  with lane review under the §3.3 procedure above.

### 3.4 SPEC — Mathematical Analysis (verification procedure)

- **Responsibility:** every load-bearing number in a packet, plan, or user report
  is either (a) produced by a tool/guard whose output is quoted, or (b) recomputed
  independently before use.
- **Inputs:** the number, its claimed derivation, the source figures.
- **Procedure:** (1) the producer states the derivation in one line (inputs +
  operation); (2) a different seat recomputes — Claude pre-reader for packet
  arithmetic (measured strength, Entry 81), coordinator tooling for register/log
  counts; (3) weights, rates and thresholds must cite their origin — a number
  imported from a range description or a priority-score weight is flagged on
  sight (the T15 failure shape); (4) disagreements are recorded, never averaged;
  (5) for load-bearing calculations, preserve alongside the result the original
  source figures, the formula, and the units, and verify the source of any
  material input — independent recomputation catches arithmetic errors, it does
  not validate the inputs, and two seats recomputing from the same wrong source
  figure is not independence (audit correction, 2026-11-19).
- **Outputs:** verified figure with derivation line, or a recorded discrepancy.
- **Quality criteria:** discrepancy count per round (target zero unresolved);
  every load-bearing figure in user reports traceable to a derivation or a guard.
- **Limitations:** catches arithmetic and derivation errors, not wrong source data;
  source verification remains NotebookLM/coordinator primary-source work.
- **Escalation:** an unresolved numeric discrepancy blocks any decision that rests
  on the figure (existing B1/B2 discipline: never force-match counts).

### 3.5 SPEC — Long-Context / Compression Fidelity (light)

- **Responsibility:** measure, rather than assume, that coordinator summaries,
  digests (§10.7) and state deltas preserve load-bearing facts.
- **Inputs:** a source document set and the summary/delta derived from it.
- **Procedure:** canary method, reusing the Entry 69 canary idea: seed each major
  state delta with the full set of currently-load-bearing facts listed explicitly
  (the delta already requires lanes to restate the most decision-relevant change —
  extend the restatement to a checklist: each lane confirms or corrects each listed
  fact); a fact a lane restates wrongly is a measured compression failure and is
  recorded in the round record. Quarterly, one past summary is re-derived from its
  sources by a non-author seat and diffed. **Known blind spot, stated openly
  (audit correction, 2026-11-19):** the canary list is chosen by the coordinator,
  so canaries detect loss only among facts already identified; they cannot detect
  an important fact omitted from the list, or a summary that preserves facts but
  changes their relationship. Mitigation, riding the existing §16.6 rule 9 frame
  challenge (no new machinery): for high-impact decisions, the reviewer must name
  at least one potentially important omitted fact — or state explicitly that they
  looked and found none — rather than merely confirming the supplied list.
- **Outputs:** per-delta fact-restatement accuracy; quarterly diff record.
- **Quality criteria:** restatement accuracy tracked per lane and for the
  coordinator's own summaries; any load-bearing fact lost in compression is a
  defect entered in the casebook family (document-integrity class).
- **Limitations:** measures preservation of listed facts only; framing loss
  (emphasis, omission of unlisted facts) is covered only by the quarterly diff.
- **Escalation:** a delta with a failed restatement is re-issued corrected before
  any round that depends on it proceeds.

## 5. Persistent knowledge architecture — current state and failure modes

### 5.1 What exists (MEASURED as present and in use)

- **MEMORY.md + daily logs + people/group pages** — user facts, decisions,
  preferences; the coordinator's long-term memory.
- **Improvement-decision ledger** (Entries 1–108) — every lane point dispositioned
  with reasons; the system's primary decision record.
- **Production casebook** (production-lessons.md, L-001…) + lessons digest +
  preflight checklist — failure knowledge with recurrence-prevention machinery.
- **Lane capability map** — per-lane measured strengths/weaknesses and routing.
- **Benchmark records** — Phase 0 baseline, cadence run #1, B1 scores, sealed keys.
- **Evidence ledger** — basis (measurement / official source / competitor data /
  user decision / none / hypothesis-with-date) for every standing rule and number.
- **Consult ledger** — operative evidence that user questions trigger consultation.
- **Premises brief + state deltas** — what the lanes are told; versioned by date.
- **Coordinator reasoning baseline + checklist** — the lanes' methods, distilled
  into coordinator procedure (B1–B21, T1–T16).

### 5.2 Known failure modes (MEASURED, with instances)

1. **Divergent copies of the same fact.** The order-watch log-vs-register gap
   (+7 rows) persists unresolved, cause unidentified, deliberately never
   force-matched. The focus plan recorded the same class at +1 earlier
   (a suspected duplicate row). Two records of one pipeline disagree and no
   reconciliation mechanism exists beyond "record the gap".
2. **Stale canonical documents.** Premises brief v1 predates §18.8, rules 14–15
   and T16 (S3). The video-stock ledger is stale. A stale canonical file is
   worse than a missing one: it is cited as authority.
3. **External mutation of memory.** MEMORY.md on disk no longer matches the
   copy injected at a session's start (background maintenance removed four
   bullets in one observed instance; the underlying source files remained the
   evidence). Any layer that can be edited outside the coordinator's own
   record is a divergence risk of the same class as (1).
4. **Rules recorded but not retrievable at the moment of action.** The
   draft-first root cause (Entry 68): verification was pull-type, fired by
   objection, provable only by self-report. The 19:15 deferral and the
   twice-repeated fastest-first breach are the same shape in different
   clothing: the knowledge existed; the trigger did not fire.
5. **Self-detection decline.** Supervisor-measured self-detection fell from
   71% to 55% — the knowledge system's feedback loop is measurably weakening
   even as its records grow.

### 5.3 Safeguards proposed (against false knowledge becoming permanent)

- **Promotion rule (already the house rule; restated as the architecture's
  core):** nothing becomes "verified/established" by consensus or repetition —
  only by measurement, official source, verified outcome, or explicit user
  decision (premises brief; A+ PILOT ONLY status). Every ledger entry carries
  its basis or is labelled hypothesis/UNCONFIRMED with a review date.
- **Single-authority rule per fact class, with named reconciliation:** each
  recurring count (pipeline stages, budget, benchmark scores) has exactly one
  authoritative file; other files cite it, never restate it (the Entry 37
  budget-ledger pattern, generalised). Where two records already diverge,
  the gap is recorded and the authority named — never averaged, never
  force-matched.
- **Version-bump coupling:** amending the A+ standard bumps the premises brief
  in the same edit or records why not (S3).
- **Decay audit:** the supervisor's daily review already sweeps unpublished
  stock and file integrity; extend its weekly pass to canonical documents
  (premises brief, capability map, routing table) with a "last verified
  against source" date per document, so staleness is a dated fact, not a
  discovery.
- **Canary facts:** the compression-fidelity canaries (§3.5) double as
  memory-integrity checks: a load-bearing fact that lanes restate wrongly
  after a delta is evidence the memory layer, not the lane, is corrupt.
- **Volume is not reliability (audit correction, 2026-11-19):** a larger
  ledger is not evidence of a more reliable system. Wherever record volume
  is reported (entries written, rounds held, cases recorded), the firing
  metrics must be reported alongside it in the same view: the
  self-detection rate (71% → 55%, §5.2 item 5) and retrieval-at-the-moment-
  of-action measures (rules that existed but did not fire). A growth in
  records with a decline in firing metrics is reported as a decline, not
  as progress.

### 7.3 Security requirements — lanes, sessions, and debugging ports (audit correction R7, 2026-11-19)

The CDP browser automation and the disposable-account session profiles
are sensitive operational surfaces. The following are standing
requirements, not aspirations:

- **Debugging ports are local-only.** Chrome remote-debugging ports
  (9222–9226) bind to 127.0.0.1 on the user's PC and are reached from
  the VM only through the SSH tunnel. They are never exposed to a public
  or LAN interface; any change to that binding stops all lane work until
  reviewed.
- **Session profiles and cookies are protected material.** The
  automation profiles live only on the user's PC; their contents
  (cookies, session state) are never copied into packets, logs, or the
  VM, and are never read beyond the presence/metadata checks the
  standing rules already permit.
- **No credentials in packets or logs.** Passwords, tokens, and codes
  never enter a packet, a round record, or a log file; credential values
  move only through the approved secure store (standing rule, restated
  here because lane tooling writes logs by default).
- **Account-identity verification — five points, fail closed [v4 —
  CD-04, re-audit RA-05; replaces the v3 single-point check].**
  Automation runs only in the dedicated disposable-account profiles.
  The operator verifies the signed-in account identity in the profile
  is the expected disposable account for that lane: **(1)** at task
  start; **(2)** before the lane's first send in any session; **(3)**
  after any browser restart or session recovery; **(4)** after any
  detected account, profile, or CDP-target change, or any unexpected
  navigation to an account page; **(5)** whenever the active identity
  cannot be verified. On any mismatch or non-verifiability: the lane
  stops immediately, nothing is sent, and the discrepancy is reported
  and recorded in the consult ledger before work resumes. The user's
  MAIN accounts are never signed into an automation profile.
- **Session revocation on compromise.** If a profile or session is
  suspected compromised: stop the lane immediately, close its browser,
  delete the affected profile's session state, and re-authenticate only
  through the user-hand step (the user signs in himself); the incident
  and the revocation are recorded in the consult ledger. A revoked
  session is never silently reused.
- **Bridge publication check [v4 — CD-05, re-audit RA-07].** Before a
  bridge packet link is handed over, the packet text is scanned for
  the standing sensitive patterns — the user's account email
  addresses, phone number, postal code, credential-shaped strings,
  and account-ledger identifiers — and the scan result (patterns
  checked; hits, or zero hits) is recorded in the rotation's
  completion record. A hit stops publication until the content is
  removed or the hit is dispositioned as a false positive in the
  record. (Data-class rule: A+ standard §4. The scan is additive; the
  §4 drafting discipline remains the primary control, and the
  completion record states both were applied.)

### 10.3 Regression thresholds and rollback (tied to §17 and the B1 baseline)

- **Regression definition:** on any post-change benchmark run under
  equivalent conditions, a seat or the coordinator falling (a) below
  the behaviour floor (any B-group item, or a missed constraint
  violation in group A), or (b) more than 2 tasks below its B1-baseline
  seeded-defect detection (the §17.4 provisional floor formula), is a
  **regression event**.
- **Interpretation (audit correction R9, 2026-11-19):** these thresholds
  are **operational triggers, not statistical proof of regression**. A
  15-task run cannot statistically establish that a change caused a
  decline. Before any regression event is attributed to a specific
  improvement (the Suspend / Roll back steps below), the record must
  show: the task-level failures identified individually, and an
  examination of the execution conditions of that run (leg availability
  and NOT OBTAINED legs, packet or key defects, environment changes)
  that could explain the failures without the improvement. Attribution
  follows that examination and is recorded in the ledger with it;
  unattributed events trigger investigation, not rollback.
- **Reject:** an improvement whose own acceptance test (§9) fails is
  rejected at the gate; it does not enter the standard.
- **Suspend:** an improvement in force that coincides with a regression
  event on the next milestone run is suspended (its standard text is
  annotated SUSPENDED with the run ID) pending disposition — the
  §17.5 below-floor machinery (classify → mechanical fix or DEGRADED
  marking → re-measure) applies to the improvement as it does to a seat.
- **Roll back:** if the regression is dispositioned as caused by the
  improvement, the standard text is reverted to the pre-change version
  (all standard amendments are ledger-recorded, so the prior text is
  recoverable from the entry + the pre-change packet record), the
  rollback is entered in the ledger with the causing run's scores, and
  the improvement may be re-proposed only with new evidence.
- **Gap stated honestly:** no automated rollback exists and none is
  proposed; rollback is a documented manual procedure over
  ledger-recorded text. There is also no continuous regression
  detection — benchmarks are milestone-based (§17.4), so a regression
  can persist undetected between milestones; the supervisor's daily
  self-detection counts are the only between-milestone signal, and
  they are currently declining (71% → 55%).
